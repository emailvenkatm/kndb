CIDR 2027 submission · internal team explainer

KNDB A database that refuses to lose the distinction between a measurement, a model's guess, and a computed aggregate.

When AI systems write into ordinary databases, a model's low-confidence prediction and a real measured fact land in the same column and look identical after the write. Every team then reinvents "how much do we trust this?" in application code, differently in every layer. KNDB pushes that distinction into the storage engine so it becomes an invariant, not a code-review checklist.

01 · the problem

Databases don't remember where facts came from

Almost every production database has one big open field for each attribute. An age is an age, a lab value is a lab value, an income is an income. Nothing in the schema says how that value got there. Whether it was measured, imputed, guessed by a model, aggregated from other rows, or copied from an unreliable partner: after the write, all of them read back the same.

That was tolerable when most writes came from careful humans and audited ETL. It stops being tolerable when the writers include LLM agents, ML enrichment pipelines, MCP tools with function-calling, and a dozen microservices that don't share a code-review process.

What actually breaks

Plain Postgres

Team A's ML pipeline imputes missing hba1c values (confidence 0.6) and writes them into the same labs.hba1c column as real lab results. Team B's clinical-trial screener queries hba1c ≥ 6.5 and recruits patients whose "lab value" was a model's guess. Nothing in the DB stopped it. Nothing in the DB even knows.

KNDB

The hba1c slot is registered as observation. When Team A's pipeline sends a write with epistemic kind inference, the write is rejected at trigger time with a specific error KNDB R5: attribute hba1c is registered as observation, got inference. The row never lands. The trial cohort stays clean.

The failure has three shapes, and we see all three in the wild.

  • Silent overwrite. A newer, worse claim replaces an older, better one and the loser vanishes.
  • Confidence laundering. A 0.6-confidence prediction joins with a 0.95-confidence measurement and the query returns something that looks 0.95.
  • Provenance loss. No one can answer "what did we believe on Tuesday?" without reading the write-ahead log by hand.
02 · the idea

Make trust a first-class database primitive

KNDB is a Postgres extension. It changes what a fact is: every row carries an epistemic kind (observation, inference, derived), a confidence in [0,1], a set of source facts it depends on, and two time ranges (when the fact was true in the world, when the database believed it).

Around that shape, five write-time and query-time rules turn the schema into a trust contract. All five are enforced by the engine, in triggers and provenance semirings, not by convention or a linter. If the invariant is worth caring about, you can't forget it, because the database will forget it for you.

The narrow claim

No relational or graph database engine ships a first-class epistemic-kind system with propagation semantics baked into query evaluation. KNDB is a minimal prototype that does, tested against real Synthea clinical data, with honest overhead numbers.

03 · why this matters now

Three forces make this the right moment

1. Agents are writing to your database

Every serious agent framework in 2026 stores memory. Zep, Graphiti, LangGraph checkpoints, MCP servers, coding agents with tool access. When these writes flow into a shared operational database, there is no schema-level distinction between what the agent knows and what the agent guessed. That's a compliance problem waiting to happen, and a reasoning problem happening already.

2. Regulated industries want provenance receipts

Healthcare (HIPAA, FDA guidance on ML-derived clinical decisions), finance (FCA/CFPB on algorithmic underwriting), pharma (21 CFR Part 11 audit trails). None of these accept "the code was reviewed" as evidence. They want a query that returns what we believed at a specific point in time, from what evidence, with what confidence.

3. The academic ground is fertile but the engine ground is empty

ProvSQL (VLDB 2018, actively maintained through 2026) gives us provenance semirings inside Postgres. TypeDB has schema-level kinds but no confidence propagation. XTDB and Datomic have bitemporal but no epistemic type. MemIR (arXiv 2605.25869, May 2026) has typed atoms but sits in an agent-memory runtime that lives above the database, so pulling the runtime pulls the guarantee. Nobody has put the whole thing into the storage engine. That's the gap KNDB fills.

04 · the five primitives, with examples

Five write-time-checked rules that add up to trust

Each of these is a real, running piece of engine code in the repo. Each has failing-test-first evidence that the engine actually catches the bug the rule claims to catch. All five stack: the paper's contribution is the coherent package.

1

Epistemic typing

Every fact is observation, inference, or derived. The database refuses to lose the distinction.

We define a Postgres ENUM domain kndb.epistemic_kind and put every fact table on it. A slot registry says "the hba1c attribute must be observation." A trigger checks that on every insert and update. derived facts additionally must reference at least one source fact by ID, so aggregates cannot lie about their inputs.

Examples

Healthcare (the one we actually ran)

An ML pipeline imputes a missing HbA1c value from other labs and writes it into labs.hba1c because "we need something there." Plain Postgres stores it silently. KNDB rejects the write: hba1c is registered as an observation-typed slot, and the pipeline's row is an inference. The trial cohort stays clean.

Lending & underwriting

Applicant leaves income blank; a model estimates $85k (confidence 0.6). Someone pushes it into applications.annual_income. The underwriter joins income with credit score and approves the loan. KNDB requires the model output to be typed inference, which the underwriter's join surface can then filter or downgrade.

CRM enrichment

A vendor enrichment API guesses a company's headcount from LinkedIn. The sales team writes that into accounts.employees alongside verified numbers from procurement. Six months later nobody remembers which is which. KNDB never lets them share the slot.

Agent memory

An agent stores "user said their birthday is March 5" (observation) and later infers "user is a Pisces" (derived). If those go in the same column, a future prompt can quote the derivation as if the user said it. KNDB refuses to store them as the same kind.

2

Confidence propagation

The engine computes joined confidence via the Viterbi semiring across query joins. No app-side arithmetic.

Every fact carries a numeric confidence in [0,1] and a matching ProvSQL provenance token. When you join two facts, the engine computes the combined confidence as their product (Viterbi = multiply-select). A 0.95 observation joined with a 0.6 inference emerges as 0.57, and it says so on the result row. Nobody has to remember to multiply anything.

Examples

Clinical trial screening

Trial T2DM-06 wants patients where "HbA1c is high AND the model says diabetic." The join between a 0.95 observation and a 0.7 model prediction should return 0.665. On our real Synthea run, KNDB returned 0.665 exactly; a naive baseline using MIN(confidence) returned 0.7, silently over-crediting the model.

Fraud detection

A transaction is flagged risky because it matches an IP-reputation signal (0.8) AND a model score (0.6). The team's dashboard shows "risk = 0.6" (min). The real Viterbi risk is 0.48. That's the difference between escalating a case and closing it.

RAG citations

A generated answer cites a retrieved document (retrieval_conf 0.9) and a model claim (generation_conf 0.7). The composite answer confidence should be 0.63. Every RAG stack reimplements this arithmetic in Python. In KNDB it's the join.

Recommendations

"User is engaged" = model prediction (0.65) x last-week click observation (0.95). Naive systems report the max, the min, or a weighted average that varies by which team asked. KNDB always says 0.62.

3

Write-time conflict detection

A contradicting claim never silently overwrites the prior one. The loser is preserved in an audit table.

When a new fact conflicts with an existing fact on the same entity in overlapping valid-time, a trigger either (a) closes the loser's system-time window and inserts the new row while copying the loser into kndb_audit, or (b) rejects the new write outright, depending on a per-attribute policy. Silent overwrite is not possible under either policy.

Examples

User profile

User's address is on file. A support script updates it from a typo in a customer email. Later the shipping team asks "what address did we have last Tuesday?" With plain Postgres, that history is gone. With KNDB, the audit table has the loser.

Inventory

Two warehouse teams update stock count within seconds. The last write wins and the first team is wrong-blamed for a discrepancy. KNDB either preserves both (invalidate policy) or refuses the second (reject policy) with a specific error saying "you conflict with row X."

Clinical diagnosis

Two clinicians enter conflicting diagnoses for overlapping periods. Plain EHR shows whichever wrote last. KNDB keeps both, with the audit trail visible to reviewers, so the resolution conversation happens on data, not on tickets.

Contact management

Marketing has one phone number, sales has another, both are "current." KNDB refuses to pretend both are current at once. Either they get different valid-time ranges (which team called on which date) or one becomes an inference with lower confidence.

4

Bitemporal validity

Every fact has a valid time (when it was true in the world) and a system time (when we recorded it). "As of date X" is a stock query.

Both times are Postgres tstzrange columns. A GiST exclusion constraint (compatible with ProvSQL's provenance column, verified on real data) prevents overlapping valid-time on the same attribute for the same entity. Two SQL functions, kndb.as_of_valid() and kndb.as_of_believed(), answer the two natural historical questions in one line.

Examples

Regulatory audit

"What was our AML risk assessment for this customer on January 3rd?" With plain Postgres and mutable rows, the answer requires an offline log query. With KNDB, it's a select.

Insurance policy

Policy is effective April 1 to June 30 but was recorded on February 15. When the claim comes in for a May incident, was the coverage in force? Two different times, two different questions, both need to be answered.

Agent memory (Zep-style)

"What did the agent believe about the user last Tuesday, based only on what it had been told by then?" is a common question during agent debugging. Plain agent-memory systems store one snapshot. KNDB answers it directly.

Backfills and corrections

A batch job discovers three months of upstream data was wrong and corrects the values. Everyone downstream should see the correction, but historical reports run on the old values must still reproduce their old results. Bitemporal makes both true at the same time.

5

Progressive-depth queries

A single knob controls how much to trust: depth 0 returns only observations; depth 1 adds inferences; depth 2 adds derived aggregates. Recall goes up, average confidence goes down, monotonically.

kndb.expand(entity_id, depth) is a set-returning function. The caller picks the trade-off explicitly per query. The paper's claim, tested on real data, is that recall never decreases and average confidence never increases as depth grows. That's a mathematical property of the epistemic kinds, not a hope.

Examples

Trial screening (strict vs broad)

The clinical protocol requires observed HbA1c only: depth 0. The recruitment team's "possible candidates" dashboard is willing to accept model-predicted diabetics: depth 1. The same query, one integer changes.

Support ticket triage

Emergency queue only looks at observations from the customer (they explicitly said the outage is affecting them). Broader queue also includes model-inferred impact. Broadest queue includes derived aggregates like "this account's error rate is up 3x."

Content moderation

Depth 0: user reports. Depth 1: model-flagged posts. Depth 2: derived signals like account age percentiles. Reviewers can pick their confidence appetite per shift.

Search & recommendations

Rank first-party click observations before hovers before model inferences before "similar users liked." A single query returns them tagged with their kind, so ranking code doesn't have to reconstruct the hierarchy.

05 · what we've actually built

Prototype status Green

Everything below runs today, with real data, under CI, on a real GitHub-hosted runner. No mocks. No fabricated numbers.

Engine

  • Five primitives implemented in ~600 lines of SQL + PL/pgSQL under engine/.
  • 15 sub-tests across 7 files, all green, every write-time rule proved by a failing test made to pass.
  • Runs on Postgres 17.10 + ProvSQL 1.10.0, pinned by SHA256 in the compose file.

Real-data demo

  • Synthea v4.0.0 generates 11,637 synthetic patients (SHA256-verified download).
  • Loaded into typed kndb.fact: 544,349 observations, 4,999 inferences (synthesized model predictions, mean confidence 0.7047), 16,239 derived aggregates.
  • Trial T2DM-06 screening returns 492 obs-eligible patients, 2,495 candidate join rows, top-5 joined Viterbi confidence 0.9025.
  • Attack: the "model imputes HbA1c into an obs-typed slot" scenario runs on a real patient with no HbA1c reading; KNDB rejects it at write time with rule R5. Row never lands.

Honest benchmark

Four baselines: KNDB, plain Postgres, Python-app-layer guards, hand-rolled trigger suite (steelman). Measured natively on ARM64 (Homebrew Postgres 17 + ProvSQL built from source, no emulation) so absolute numbers are quotable.

Two honest findings from real numbers, both worth reporting in the paper:

  1. The steelman ties on correctness. A careful hand-rolled trigger suite gets the same 70/70 catch and the same exact confidence numbers as KNDB. Our story is not "no one else can do this." It is "here is what those primitives look like as a coherent, tested package, so nobody has to reimplement them per project."
  2. KNDB throughput drops with table size, the steelman does not. On the 565k-row Synthea database, KNDB does 5,597 writes/sec; the steelman does 15,559. The gap comes from ProvSQL's set_prob map growing with the table. That is the honest cost of engine-computed confidence propagation, and the steelman avoids it by not implementing propagation at all.

CI, reproducibility, and infra

  • GitHub Actions runs bootstrap, engine apply, both smoke tests, and all 5 primitive tests on every push. 5 consecutive green runs so far.
  • One command reproduces the entire pipeline: make reproduce.
  • Image, extension, Python, seed, kernel and CPU governor all logged into bench/results/manifest.json per run.

07 · how KNDB differs from adjacent systems

Everyone else has some of it. Nobody has all of it in the engine.

Two neighbors reviewers will pattern-match against and we must differentiate against explicitly:

  • MemIR (arXiv 2605.25869, May 2026) ships typed atoms with write-time claim authorization in an agent-memory runtime. Pull the runtime and the guarantee is gone. KNDB puts the same idea in the storage engine, so it survives every client.
  • ATCH / Equivalence Theorem (arXiv 2603.13603, Feb 2026) formalizes the four-property completeness (n-ary + temporal + uncertainty + causal). It is a theorem paper. KNDB is the shipping mechanism, with honest overhead numbers on real data.
08 · try it

Fifteen minutes and you have it running

git clone git@github.com:emailvenkatm/kndb.git
cd kndb
make up            # starts isolated Postgres + ProvSQL on port 5433
make engine        # applies engine/*.sql
make test          # 15/15 sub-tests pass
make demo          # the 60-second trust story

For the real clinical scenario on 11,637 Synthea patients: 

bash data/generate.sh       # downloads Synthea v4.0.0 (SHA256 verified), takes ~10 min
python3 data/synthesize_labels.py
bash data/load_postgres.sh
bash demo/demo_clinical.sh  # attack + eligibility screening on real data

For the benchmark: 

bash bench/run_native.sh       # native ARM64 (no emulation) if brew Postgres is installed
bash bench/run_synthea.sh      # same benchmark on 565k Synthea-preloaded rows

Everything else is in STATUS.md at the repo root, which is the "safe to quote in the paper" reference.
