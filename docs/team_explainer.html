Team explainer. CIDR 2027 submission

A database that remembers which numbers were measured, which were calculated, and which were guessed.

AI agents and enrichment pipelines now write model-generated data into operational databases at scale, next to verified facts, with no origin distinction at the storage layer. KNDB makes that distinction a first-class part of the storage engine, so origin survives ETL, sync, MDM survivorship, compliance audits, and years of downstream analytics.

TL;DR
  • Every row carries a kind: MEASURED, INFERRED, or DERIVED. The engine refuses to lose the distinction.
  • A precedence lattice (kind rank, then specificity, then confidence, then arrival) decides survivorship at write time so a fresher-but-unverified value cannot silently overwrite a MEASURED one.
  • Three engine-provided views (fact_compliance, fact_analytics, fact_training_safe) give compliance, analytics, and model-training paths different visibility on purpose.
  • Prototype green on Postgres 17 + ProvSQL. 26 sub-tests pass, 9-step smoke gate wired into CI. CIDR 2027 submission by 2026-08-04.
Substrate: Postgres 17 + ProvSQL 1.10.0 Repo: github.com/emailvenkatm/kndb

01 · the idea

Trust as a first-class storage primitive

Look at any operational database column and ask: is this number measured, calculated from a formula, or predicted by a model? In a plain SQL store, the schema does not say. Every downstream query treats the three as equal. Every team then reinvents "how confident is this?" in application code, differently each time. When the answer matters, the difference is invisible.

KNDB is a Postgres extension. Every row carries an epistemic kind (MEASURED, INFERRED, or DERIVED), a confidence in [0, 1], a set of source facts it depends on, and two time ranges (when the fact was true in the world, and when the database believed it). Around that shape, five write-time and query-time rules turn the schema into a trust contract enforced by the engine itself, not by a linter or a code review.

The narrow claim

No relational or graph database engine ships a first-class epistemic-kind system with confidence propagation baked into query evaluation. KNDB is a minimal prototype that does, tested against real Synthea clinical data with measured overhead.

02 · where it breaks in practice

Four everyday cases where the column doesn’t say what kind of number it is

Four independent evidence lines say this is the shape of the problem. Each has a primary source and each maps onto a specific KNDB primitive.

MDM survivorship

A fresher CRM address overwrites a postal-verified one

MDM survivorship rules ranked by recency are common. A CRM sync writes a fresher shipping address for a customer whose current address on file was postal-verified last quarter. The fresher row wins by timestamp, and the verified one is gone.

Pattern
Recency-first survivorship treats every source as equal. The fact that the postal service confirmed one and a CRM sync guessed the other is lost.
Fails as
Shipping labels print to the newer, unverified address. Bounced parcels. Regulatory KYC drift.
Traditional DB fails: last-write-wins on a single address column. No engine-visible distinction between MEASURED (postal verification) and INFERRED (CRM sync).
KNDB catches: the CRM row lands as INFERRED (kind rank 1), the postal row is MEASURED (kind rank 3). The lattice refuses to displace the MEASURED row. The INFERRED write is audited with reason kind_outranked.
Source: Validity, Poor data quality is sabotaging businesses in 2022. More than half of surveyed CRM admins rate accuracy and completeness below 80 percent.
CRM enrichment accuracy

Vendor model guess lands in accounts.employees next to verified counts

Contact and firmographic enrichment vendors return model-guessed values when they don’t have hard data. Those values ship into the CRM column that also holds verified employee counts. Marketing cohorts join on the column without knowing which is which.

Pattern
Enrichment API writes a modeled headcount into the same integer column as an SEC-filed count. Two very different levels of ground truth, one storage cell.
Fails as
Marketing spends on cohorts sized by model guesses. Sales opportunity scoring inherits the same bias. Nobody can separate verified accounts from enriched ones without reverse-engineering the vendor’s API.
Traditional DB fails: one integer column, no kind, no confidence, no source pointer per row.
KNDB catches: enriched value lands as INFERRED with the vendor’s confidence; the verified count stays MEASURED. Campaign query hits kndb.fact_analytics to include both, or kndb.fact_compliance to exclude the model guesses on purpose.
Source: Validity, State of CRM Data Management in 2025. 76% of CRM users say less than half of their CRM data is accurate and complete.
CFPB explainability

Adverse-action letter for a model-driven credit denial

CFPB Circular 2023-03 requires creditors using AI or complex algorithms to give the specific, accurate reasons behind an adverse action. There is no special exemption for AI. The adjudicator preparing the letter needs to see exactly the evidence the model saw, and needs to keep the model’s own guesses out of the audit trail.

Pattern
Credit-decision model consumes measured and inferred features together. When the letter needs to name the reasons, the origin of each feature is not stamped on the row.
Fails as
Adjudicators cite “algorithmic decision,” which the regulator has said is not enough. Enforcement action.
Traditional DB fails: the feature table stores the model input without an origin flag. Reconstructing the audit trail is manual.
KNDB catches: adjudicator queries kndb.fact_compliance, which excludes INFERRED by default and returns only MEASURED and DERIVED evidence. The letter can cite the specific measured facts that drove the decision.
Source: CFPB Circular 2023-03. “Creditors must be able to specifically explain their reasons for denial. There is no special exemption for artificial intelligence.”
Training-data decontamination

New model ingests another model’s prior output as ground truth

Training a next-generation model on data pulled from an operational warehouse means pulling both real observations and prior model output that got stored in the same columns. Shumailov et al. (Nature 2024) show that recursive training on model-generated data leads to irreversible model collapse. Keeping model output out of the training corpus is a real engineering task.

Pattern
Prior model’s inferences are indistinguishable from measurements in the warehouse column. Training pipeline pulls whatever the column contains.
Fails as
Model collapse: tails of the distribution disappear, the model loses variance and rediscovers its predecessor’s errors.
Traditional DB fails: no engine-visible way to select “only ground truth” without a hand-maintained convention.
KNDB catches: training pipeline selects from kndb.fact_training_safe, which returns MEASURED rows only. Prior model output is not visible through that view at all. The model-collapse feedback loop is broken at the storage layer.
Source: Shumailov et al., AI models collapse when trained on recursively generated data, Nature 631 (2024).
The one to remember

Same underlying problem in every case: the database does not know which value came from a measurement and which came from a model. KNDB makes that a schema-level distinction the engine can enforce at write time and expose at read time.

When the same failure mode was reported at scale

Same underlying problem, the database forgot which values were measured, blown up to lawsuits, retractions, and regulator actions. Every URL below was checked; the full ten-case detail is linked at the bottom of this section.

Ambient AI

Nabla / Whisper hallucinations in signed clinical notes

~85 US health systems, ~7M encounters. Whisper-based ambient scribes hallucinated content into clinician-signed notes. Cornell and UW researchers logged hallucinations in ~1% of ~13,000 clean audio segments. Nabla's CTO confirmed source audio is deleted "for data safety." Once a fabrication is signed, no ground truth remains.

Source: Cohen Milstein docket page

Zillow Offers. Zestimate consumed as purchase-price signal

Zillow shut down iBuying in November 2021. Root cause per Stanford GSB: the algorithmic Zestimate was treated as sufficient signal to bid. Downstream systems never distinguished "model prediction" from "verified comparable." 25% workforce cut.

Source: Stanford GSB post-mortem
$2.7M CFPB penalty

Hello Digit. ML “safe amount” executed as authorized ACH debit

The autosave algorithm estimated a "safe" transfer amount. Downstream banking rails executed those estimates as authorized ACH debits. Roughly 70,000 overdraft reimbursement requests since 2017. CFPB $2.7M penalty plus $68,145 in redress.

Peer-reviewed

Epic Sepsis Model. External validation missed 2/3 of cases

Wong et al. externally validated the vendor-shipped Epic Sepsis Model at Michigan Medicine across 38,455 hospitalizations. It missed about two-thirds of sepsis cases and drove massive alert fatigue. The score is written to the EHR every 15 minutes. Downstream analytics consumed it as observed risk. Hundreds of hospitals inherited the model before independent validation existed.

FDA's Predetermined Change Control Plan guidance (Feb 2025) and ONC's HTI-1 DSI rule (Jan 2025) both regulate the model. Neither requires that a value written back to the chart carry a persistent epistemic-kind flag. That is the storage-layer gap KNDB fills.

04 · the six primitives

Six engine-enforced rules that add up to trust

Each is a real, running piece of engine code in the repo. Each has failing-test-first evidence that the engine actually catches the bug the rule claims to catch. Each is presented below with its analogy, a traditional-DB-fails vs KNDB side-by-side, and two realistic examples.

1

Epistemic typing and specificity

Every fact is typed MEASURED, INFERRED, or DERIVED, and carries a numeric specificity (0 for a batch loader, 100 for a normal per-entity write, higher for an adjudicated correction). The engine refuses to accept a wrong-kind write, and refuses to accept a DERIVED row that does not name its sources.

Analogy · the newsroom Every claim in the paper is tagged reporter-confirmed, off-the-record source, or editor’s summary. The copy desk refuses to send an editor’s summary out under a reporter-confirmed byline.
Traditional DB

Any writer can push any number into any column. Vendor-enriched employee count lives in the CRM table next to an SEC-filed count. Nothing enforces the distinction; downstream code has to remember.

KNDB

The SEC-filed row is registered as MEASURED, the enrichment row as INFERRED. Every write is checked at the trigger; a wrong-kind write is rejected before the row lands, no matter which client sent it.

MDM survivorship

A CRM sync attempts to write a fresher but unverified shipping address on top of a postal-verified address. In KNDB the CRM row lands as INFERRED with the CRM’s confidence; the postal row stays MEASURED. Downstream shipping queries keep printing to the verified address.

Sales & CRM enrichment

Vendor enrichment fills in accounts.employees for unknown companies with model guesses. In KNDB verified counts stay MEASURED, model guesses land as INFERRED. Marketing cohorts can query either or both, on purpose.

2

Confidence propagation via Viterbi semiring

Every fact carries a numeric confidence in [0, 1] and a matching ProvSQL provenance token. When you join two facts, the engine computes joined confidence as the product. A 0.95 MEASURED joined with a 0.7 INFERRED emerges as 0.665. Nobody has to remember to multiply anything.

Analogy · the weather chain 80% chance of sun and 60% chance the picnic invite is real = 48% you go on a sunny picnic. Every “and” multiplies, and the DB does the multiplying so every team gets the same answer.
Traditional DB

Team A reports the joined confidence as MIN(0.95, 0.7) = 0.7. Team B averages to 0.825. A dashboard shows 0.95. Same underlying facts, three answers. Meetings ensue.

KNDB

The join returns 0.665, computed by the engine’s Viterbi semiring. Every team asking the same question gets 0.665. One number, one place, one truth.

Fraud detection

Transaction flagged by an IP-reputation signal (0.8) AND a model score (0.6). The team dashboard shows “risk = 0.6” (min). Real Viterbi risk is 0.48. That’s the difference between escalating a case and closing it.

Marketing scoring

Lead score is (fit MEASURED at 0.9) times (intent INFERRED at 0.5) = 0.45 on the KNDB engine. Naive MIN gives 0.5 and silently over-credits the model. Same input, different pipeline, one answer that survives audit.

3

Write-time precedence lattice

When a new fact overlaps an existing live fact on the same entity, attribute, and valid-time and the values differ, the engine picks a survivor by an explicit lattice: kind rank (MEASURED > DERIVED > INFERRED), then specificity, then confidence, then arrival. The loser is copied to the audit table with one of four reason codes: kind_outranked, specificity, confidence, contradicted_same_rank. Silent overwrite is not possible.

Analogy · the newsroom copy desk A tip from an anonymous source cannot overwrite a photographed receipt. A high-confidence guess is still a guess. Rank matters more than certainty.
Traditional DB

Last-write-wins. A fresher CRM address silently overwrites the postal-verified one. Six months later a shipping team asks “what address did we have that was actually verified?” and the answer is gone.

KNDB

The lattice reads MEASURED > INFERRED. The postal row stays live. The CRM row is refused and audited with reason kind_outranked. Reversing the arrival order does not change the outcome.

MDM survivorship

A high-confidence INFERRED (0.97) that arrives after a lower-confidence MEASURED (0.90) is refused. The MEASURED row stays live. The audit table records reason kind_outranked. This is test T3.4 in the suite.

Inventory ownership

Two warehouse teams update stock count within seconds. Same kind, same specificity, higher-confidence wins; if all three tie, arrival decides and the prior version is audited with contradicted_same_rank. No silent divergence between shift reports.

4

Bitemporal validity

Every fact has a valid time (when it was true in the world) and a system time (when we recorded it). “As of date X” is a stock query. Two SQL functions, kndb.as_of_valid() and kndb.as_of_believed(), answer the natural historical questions in one line.

Analogy · a newspaper archive with corrections You can read the article as printed on March 5 (what we thought that day) or the correction issued March 12 (what turned out to be true). Both are queryable, neither is lost.
Traditional DB

Corrections mutate the article in place. Ask “what did the March 5 paper say?” and you get what we think NOW, not what was on the newsstand then. Audits require reading the write-ahead log by hand.

KNDB

Both the March 5 belief and the March 12 correction live in the table with their respective time ranges. Either question is a stock query. Audits are ordinary SQL.

Regulatory audit

Regulator asks: was Jane properly approved for the loan on Feb 15 based on what you knew then? In plain Postgres the DB shows only current state; a Mar 20 correction masks the Feb 15 belief. In KNDB, as_of_believed('2026-02-15', '2026-02-15') returns exactly what the credit team saw at approval. Decision defended in one query.

Insurance policy effective dates

Policy is effective April 1 through June 30 but was recorded on February 15. When the claim comes in for a May incident: was the coverage in force? Two different times, two different questions, both must be answerable.

5

Progressive-depth queries

One SQL function, kndb.expand(entity, depth), controls how much to trust. Depth 0 returns only MEASURED. Depth 1 adds INFERRED. Depth 2 adds DERIVED aggregates. Recall goes up, average confidence goes down, monotonically.

Analogy · triage lanes Same waiting room, three lanes. Immediate (only confirmed observations). Urgent (also model-flagged). Non-urgent (also derived signals). One knob, the same data, the right people first.
Traditional DB

Every filter is a different query. Strict-mode team writes one WHERE clause. Broad-mode team copies and adds an OR. Each team’s numbers diverge over time.

KNDB

One knob. kndb.expand(depth=0) is MEASURED only. depth=1 adds INFERRED. depth=2 adds DERIVED aggregates. Same query shape, one integer changes.

Support ticket triage

Emergency queue: only observations from the customer (they explicitly said the outage is affecting them). Broader queue: also model-inferred impact. Broadest queue: also derived signals like “this account’s error rate is up 3x.” Reviewers pick their confidence appetite per shift.

Content moderation

Depth 0: user reports. Depth 1: model-flagged posts. Depth 2: derived signals like account age percentiles. Moderators tune the tradeoff without reimplementing filters every quarter.

6

Use-permission views

Three engine-provided views over kndb.fact make the query scope the shape of the object you select from, not a WHERE clause someone can forget. kndb.fact_compliance filters to MEASURED and DERIVED. kndb.fact_analytics includes all kinds. kndb.fact_training_safe filters to MEASURED only.

Analogy · the library reading rooms The same collection, three rooms. Public reading room shows verified references. Analytics room shows everything indexed. Training room shows only primary sources. The room enforces what you can pull off the shelf.
Traditional DB

Every application team writes its own filter. Compliance script forgets to exclude model output. Training script pulls last quarter’s inferences as if they were observations. Nobody enforces the boundary.

KNDB

The boundary is a schema object. Compliance queries hit fact_compliance. Analytics queries hit fact_analytics. Training pipelines hit fact_training_safe. Selecting from the wrong view yields the wrong shape, visibly.

CFPB explainability

The adjudicator writing the adverse-action letter queries kndb.fact_compliance. INFERRED rows do not appear. The letter cites only MEASURED and DERIVED evidence, so the specific reasons the regulator requires are on hand.

Training-data decontamination

The model training pipeline selects features from kndb.fact_training_safe. Prior model output (INFERRED) does not appear. The next model does not ingest its predecessor’s guesses as ground truth. This is the storage-side answer to the model-collapse feedback loop.

05 · architecture

How it’s built

KNDB is a Postgres extension pattern, not a new server. Any team that already runs Postgres can adopt it without swapping infrastructure. The engine sits between the client and the fact table as a set of triggers and typed columns.

Client layer
psql, ORM (SQLAlchemy, Prisma, Django ORM), agent memory writers (Zep, Graphiti, MCP tool servers), MLOps pipelines (dbt, Airflow, Prefect). Every write goes through the same triggers, so no client can bypass the rules.
Write-time enforcement (PL/pgSQL triggers)
BEFORE INSERT / UPDATE triggers enforce five kind rules:
  R1. DERIVED rows must name at least one source.
  R2. Every source must resolve to an existing fact.
  R3. MEASURED rows cannot have sources.
  R4. INFERRED rows cannot claim confidence = 1.0.
  R5. Slot-kind registry must agree with the row’s kind.
A separate BEFORE trigger runs the precedence lattice on overlapping valid-time: kind rank (MEASURED > DERIVED > INFERRED), then specificity, then confidence, then arrival. The loser is copied to kndb_audit.evicted_fact with one of four reason codes (kind_outranked, specificity, confidence, contradicted_same_rank).
The fact table, kndb.fact
Columns: entity_id, attribute, value, epistemic_kind (ENUM: MEASURED, INFERRED, DERIVED), confidence (0-1 domain), specificity smallint, sources uuid[], valid_time tstzrange, sys_time tstzrange, and a hidden provsql UUID token. A GiST exclusion constraint enforces no-overlap on (entity_id, attribute, valid_time). Audit sits in a sibling table kndb_audit.evicted_fact.
Confidence propagation via ProvSQL 1.10.0
An AFTER trigger keeps set_prob(token, confidence) in lockstep with the row’s confidence. Query-side helpers call sr_viterbi(provenance(), weights_tbl) to compute joined confidence across arbitrary joins. Standard SQL joins work as usual; the semiring evaluation is opt-in per query.
Query surface and use-permission views
kndb.as_of_valid(entity, attribute, ts) for “what did we believe held at time X.”
kndb.as_of_believed(entity, attribute, valid_ts, sys_ts) for “what did we know on system-time Y.”
kndb.expand(entity, depth) for progressive-depth queries.
kndb.fact_compliance excludes INFERRED. kndb.fact_analytics includes all kinds. kndb.fact_training_safe is MEASURED only. Everything else is ordinary SQL.

06 · status

What runs today Green

All numbers below come from actual runs, seed 42, on native ARM64 Postgres 17.10 + ProvSQL 1.10.0. Nothing extrapolated.

  • Six primitives implemented in ~600 lines of SQL / PL-pgSQL. Precedence lattice, specificity column, three use-permission views wired in as part of the v2 upgrade.
  • 26 sub-tests, all pass. Includes T3.4 through T3.9 for the lattice tie-breakers and T6.1 for the use-permission views. Every write-time rule proved by failing-test-first.
  • Synthea v4.0.0 generates 11,637 patients (SHA256 verified). Loaded into typed kndb.fact: 544,349 MEASURED, 4,999 INFERRED, 16,239 DERIVED.
  • Real-data attack: model-imputed value into a MEASURED-typed slot is rejected at write time with rule R5.
  • 9-step smoke gate under two minutes, wired into CI as the final step. CI green on hosted GitHub runner.

Benchmark against three baselines

System Adversarial catch Confidence drift Guard LOC p50 latency Throughput

Two findings from the benchmark worth calling out:

  1. A hand-rolled trigger suite can catch every adversarial write in 124 lines of PL/pgSQL. KNDB's value is that those primitives ship as one coherent tested package, so every project doesn't reimplement them from scratch (and get subtly different answers each time).
  2. KNDB write throughput drops with table size (13,150 to 5,597 rps at 565k rows). The steelman is size-invariant. The gap is ProvSQL’s set_prob map growing with the table, the measurable cost of engine-computed confidence propagation.

08 · try it

Fifteen minutes and you have it running

git clone git@github.com:emailvenkatm/kndb.git
cd kndb
make up            # starts isolated Postgres + ProvSQL on port 5433
make engine        # applies engine/*.sql
make test          # 26 sub-tests pass
make smoke         # 9-step end-to-end proof of every primitive
make demo          # the 60-second trust story

For the real clinical scenario on 11,637 Synthea patients:

bash data/generate.sh       # downloads Synthea v4.0.0 (SHA256 verified)
python3 data/synthesize_labels.py
bash data/load_postgres.sh
bash demo/demo_clinical.sh  # attack + eligibility screening on real data

For the benchmark:

bash bench/run_native.sh       # native (no emulation) if brew Postgres is installed
bash bench/run_synthea.sh      # same benchmark on 565k Synthea-preloaded rows
