Team explainer · CIDR 2027 submission

A database that remembers which numbers were measured, which were calculated, and which were guessed.

Every serious operational database today stores a column of numbers with no schema-level distinction between a real measurement, an equation output, and a model prediction. KNDB makes that distinction a first-class part of the storage engine so it survives ETL, sync, and years of downstream analytics.

TL;DR
  • Every row carries a kind: MEASURED, INFERRED, or DERIVED. The engine refuses to lose the distinction.
  • The engine also computes joined confidence across queries, preserves conflicts in an audit table, and answers "what did we believe on Tuesday" as a stock query.
  • Prototype green on Postgres 17 + ProvSQL. All tests pass on 11,637 real synthetic-patient rows. CIDR 2027 submission by 2026-08-04.
Substrate: Postgres 17 + ProvSQL 1.10.0 Repo: github.com/emailvenkatm/kndb

01 · the idea

Trust as a first-class storage primitive

Look at any operational database column and ask: is this number measured, calculated from a formula, or predicted by a model? In a plain SQL store, the schema does not say. Every downstream query treats the three as equal. Every team then reinvents "how confident is this?" in application code, differently each time. When the answer matters, the difference is invisible.

KNDB is a Postgres extension. Every row carries an epistemic kind (MEASURED, INFERRED, or DERIVED), a confidence in [0, 1], a set of source facts it depends on, and two time ranges (when the fact was true in the world, and when the database believed it). Around that shape, five write-time and query-time rules turn the schema into a trust contract enforced by the engine itself, not by a linter or a code review.

The narrow claim

No relational or graph database engine ships a first-class epistemic-kind system with confidence propagation baked into query evaluation. KNDB is a minimal prototype that does, tested against real Synthea clinical data with measured overhead.

02 · where it breaks in practice

Everyday cases where the column doesn’t say what kind of number it is

Patterns that ship in normal hospitals and normal data stacks today. Each has a primary source.

Lab

eGFR — a calculation living in the lab table

eGFR is not measured. It is derived from serum creatinine, age, and sex, using MDRD, CKD-EPI 2009 (race-adjusted), or CKD-EPI 2021 (race-free refit). Labs cut over between 2021 and 2024. The LIS often kept the same result row and same LOINC code before and after.

Pattern
Model output stored in lab_results under a generic eGFR name. Which equation ran is in a comment field, or nowhere.
Fails as
A cohort spanning the 2021 refit contains mixed equations. Black patients reclassify upward, non-Black patients downward. Longitudinal CKD-progression queries fabricate progression that is pure equation change.
Traditional DB fails: one LOINC, one numeric column, no equation-version field. LOINC guidance itself says the equation "may be" transmitted in a comment.
Source: LOINC brief on eGFR codes · NKF Lab Engagement WG, Clin Chem 2022
Vitals

BMI — half-measured, half-remembered, stored as one number

BMI is computed over height and weight. Height in the EHR is usually self-reported and rarely re-measured. Weight is measured today, but the "current" row may be six months old. BMI in the vitals table looks like a vital sign.

Fails as
Self-reported BMI biased 0.42 kg/m² low. 30–40% misclassification at category boundaries. Six of eight mortality hazard ratios detectable in measured BMI vanish with self-report.
Traditional DB fails: vitals table stores the number, not the mixture of measurement modes and vintages behind it.
Source: Stommel & Schoenborn, PMC3040787
Scores

Clinical calculators written to flowsheets like vitals

Automated SOFA and APACHE II run inside Epic and Cerner and land in flowsheet rows shaped exactly like a temperature or heart rate. Retrospective researchers pull them without knowing which variables were imputed, which were carried forward, or which version of the calculator ran on that admission.

Fails as
Prospective validation of an EHR-integrated SOFA showed calibration drift from missing GCS and Pa/Fi imputations. Downstream sepsis-outcome studies inherit that drift as if it were signal.
Traditional DB fails: flowsheet schema has no "derived-from" edge, no equation version, no imputation flag.
Source: Aakre et al., IJMI 2017
CDS

Epic Sepsis Model — score refreshed every 15 min, indexed as if observed

The Epic Sepsis Model and the Rothman Index write continuous risk scores into the EHR that downstream tables treat as time-series observations. ESM famously ingested antibiotic orders as a feature (label leakage), so its "prediction" partly encoded the clinician's own suspicion. Rothman rolls up 26 EHR variables into a single number indistinguishable from a vital.

Fails as
External validation at Michigan Medicine flagged poor calibration. STAT reported ESM alerts firing after antibiotics were already ordered, making a "leading" indicator a lagging one.
Traditional DB fails: no epistemic_kind=INFERRED tag, no model-version pointer, no input-feature manifest on the row.
Source: STAT News 2021 · JAMIA Open 2024
Interop

FHIR Provenance — the resource almost nobody actually sends

FHIR defines a Provenance resource that can carry who authored a value, from what device, under which agent. In practice US Core marks Provenance "SHOULD support" for Observation and DocumentReference, and vendors implement it inconsistently. When data flows through Care Everywhere or a TEFCA QHIN, provenance frequently drops off the wire.

Fails as
Receiving EHR files the value under the local patient record. Local analytics see it as a native measurement, not knowing it came from an outside record with different equations and calibration.
Traditional DB fails: ingestion pipelines have no column for "origin system" on a per-row basis. Provenance is discarded to fit the local schema.
Source: US Core Basic Provenance IG
Data lake

Nightly ETL imputation — nulls filled before the mart is queried

Data-engineering teams routinely last-observation-carried-forward, mean-fill, or model-impute EHR labs during nightly dbt runs to make downstream joins usable. The imputed value ends up in the mart column identical to a measured value. The imputation flag lives in a sibling column that most analysts do not join.

Fails as
Cohort analyses treat imputed labs as observed. Bias is worst in patients with the least data — exactly the ones the study cares about.
Traditional DB fails: imputation is a transformation step. The resulting column has no first-class kind marker. dbt column-level lineage helps but does not carry per-row provenance.
Source: Getzen et al., PMC10280351 — missing EHR data impacts CER
MLOps

Feature stores — a feature is a feature

Feast, Tecton, and Databricks feature store enforce point-in-time correctness. They do not distinguish "feature computed from a raw measurement" from "feature computed by an upstream model." A downstream model can consume another model's prediction as if it were ground truth. Retraining loops amplify the effect.

Fails as
Silent model-on-model dependency. When Model A drifts, Model B degrades in a way the feature store cannot flag.
Traditional DB fails: feature-view schema captures type and freshness, not epistemic kind.
Source: commonly discussed in the MLOps community (Feast docs, MLOps.community). No single primary incident report cited in this pass.
The one to remember: eGFR

Every patient's kidney number on their last physical is an eGFR. It looks like a lab result. It is not measured; it is calculated by an equation that quietly changed between 2021 and 2024, and the same LOINC code was used before and after. The same patient's eGFR can jump 8 points overnight with no change in creatinine, purely because the LIS swapped equations. The database has no way to say what kind of number this is.

03 · when it made the news

When the same failure mode was reported at scale

Same underlying problem — the database forgot which values were measured — blown up to lawsuits, retractions, and regulator actions. Every URL below was checked; the full ten-case detail is linked at the bottom of this section.

Ambient AI

Nabla / Whisper hallucinations in signed clinical notes

~85 US health systems, ~7M encounters. Whisper-based ambient scribes hallucinated content into clinician-signed notes. Cornell and UW researchers logged hallucinations in ~1% of ~13,000 clean audio segments. Nabla's CTO confirmed source audio is deleted "for data safety." Once a fabrication is signed, no ground truth remains.

Source: Fortune, Oct 26 2024
$7B damages sought

DZ Reserve v. Meta — modeled audience sold as measured metric

Meta's "Potential Reach" was a modeled estimate but was surfaced in the ad-buying API as if it were a measured audience count. Plaintiffs allege 200-400% inflation. Ninth Circuit affirmed class cert. Supreme Court declined to intervene. Jury trial vacated October 2025.

Source: Cohen Milstein docket page
$569M writedown

Zillow Offers — Zestimate consumed as purchase-price signal

Zillow shut down iBuying in November 2021. Root cause per Stanford GSB: the algorithmic Zestimate was treated as sufficient signal to bid. Downstream systems never distinguished "model prediction" from "verified comparable." 25% workforce cut.

Source: Stanford GSB post-mortem
$2.7M CFPB penalty

Hello Digit — ML "safe amount" executed as authorized ACH debit

The autosave algorithm estimated a "safe" transfer amount. Downstream banking rails executed those estimates as authorized ACH debits. Roughly 70,000 overdraft reimbursement requests since 2017. CFPB $2.7M penalty plus $68,145 in redress.

Source: CFPB press release
Peer-reviewed

Epic Sepsis Model — external validation missed 2/3 of cases

Wong et al. externally validated the vendor-shipped Epic Sepsis Model at Michigan Medicine across 38,455 hospitalizations. It missed about two-thirds of sepsis cases and drove massive alert fatigue. The score is written to the EHR every 15 minutes. Downstream analytics consumed it as observed risk. Hundreds of hospitals inherited the model before independent validation existed.

Source: Wong et al., JAMA Intern Med 2021;181(8):1065
Regulators see the gap. None have closed it.

FDA's Predetermined Change Control Plan guidance (Feb 2025) and ONC's HTI-1 DSI rule (Jan 2025) both regulate the model. Neither requires that a value written back to the chart carry a persistent epistemic-kind flag. That is the storage-layer gap KNDB fills.

Full ten-case detail: research_incidents.html.

04 · the five primitives

Five engine-enforced rules that add up to trust

Each is a real, running piece of engine code in the repo. Each has failing-test-first evidence that the engine actually catches the bug the rule claims to catch. Each is presented below with its analogy, a traditional-DB-fails vs KNDB side-by-side, and two realistic examples.

1

Epistemic typing

Every fact is typed MEASURED, INFERRED, or DERIVED. The engine refuses to lose the distinction, refuses to accept a wrong-kind write, and refuses to accept a DERIVED row that does not name its sources.

Analogy · the newsroom Every claim in the paper is tagged reporter-confirmed, off-the-record source, or editor's summary. The copy desk refuses to send an editor's summary out under a reporter-confirmed byline.
Traditional DB

Any writer can push any number into any column. eGFR (calculated) lives in the lab table next to sodium (measured). Nothing enforces the distinction; downstream code has to remember.

KNDB

eGFR is registered as DERIVED, sodium as MEASURED. Every write is checked at the trigger; a wrong-kind write is rejected before the row lands, no matter which client sent it.

Healthcare

An ETL job imputes missing HbA1c values from patient history for dashboard completeness. It attempts to write them into labs.hba1c. KNDB rejects: hba1c is observation-typed, the ETL row is inference. Analysts querying labs.hba1c keep seeing measured values only.

Sales & CRM

Vendor enrichment fills in accounts.employees for unknown companies with model guesses. In KNDB, verified counts stay MEASURED, model guesses land as INFERRED in a separate stream. Marketing cohorts can query either or both, on purpose.

2

Confidence propagation via Viterbi semiring

Every fact carries a numeric confidence in [0, 1] and a matching ProvSQL provenance token. When you join two facts, the engine computes joined confidence as the product. A 0.95 observation joined with a 0.7 inference emerges as 0.665. Nobody has to remember to multiply anything.

Analogy · the weather chain 80% chance of sun and 60% chance the picnic invite is real = 48% you go on a sunny picnic. Every "and" multiplies, and the DB does the multiplying so every team gets the same answer.
Traditional DB

Team A reports the eligibility confidence as MIN(0.95, 0.7) = 0.7. Team B averages to 0.825. A dashboard shows 0.95. Same underlying facts, three answers. Meetings ensue.

KNDB

The join returns 0.665, computed by the engine's Viterbi semiring. Every team asking the same question gets 0.665. One number, one place, one truth.

Trial screening (real numbers from our Synthea run)

HbA1c observation (0.95) joined with model-predicted is_diabetic (0.70) returns 0.665 on the KNDB engine, exactly matching closed-form Viterbi. A naive baseline using MIN(confidence) returns 0.7 and silently over-credits the model.

Fraud detection

Transaction flagged by an IP-reputation signal (0.8) AND a model score (0.6). The team dashboard shows "risk = 0.6" (min). Real Viterbi risk is 0.48. That's the difference between escalating a case and closing it.

3

Write-time conflict detection

When a new fact conflicts with an existing fact on the same entity in overlapping valid-time, the engine either invalidates the loser (closing its system-time window and copying it into the audit table) or rejects the new write outright, depending on per-attribute policy. Silent overwrite is not possible under either policy.

Analogy · Git for facts Two writers cannot silently clobber each other. Either the DB merges cleanly, or it makes the conflict visible and keeps the loser's version in history.
Traditional DB

Last-write-wins. Two teams update Jane's address within the same hour; whoever hits save last is the winner. No merge dialog, no record of what got clobbered. Six months later a shipping team asks "what address did we have on Tuesday?" and the answer is gone.

KNDB

The Tuesday version's valid-time window closes when the newer write lands. Both rows still exist in the table. The audit surface lets the shipping team recover exactly what was on file at Tuesday's snapshot.

Two labs, one patient

Jane's HbA1c is 7.2 (Jan 15, Lab X) then 5.4 (Mar 20, Lab Y after starting metformin). Both claim to hold on Feb 1. In a plain EHR the Mar write silently overwrites. In KNDB the Jan window closes at Mar 20; the audit table has the loser; a regulator asking "what did we have on Feb 1" gets 7.2 as the correct answer.

Inventory ownership

Two warehouse teams update stock count within seconds. Traditional DB: last-write-wins, silently. KNDB: refuses the second write (reject policy) or preserves both with the audit surface (invalidate policy). No silent divergence between shift reports.

4

Bitemporal validity

Every fact has a valid time (when it was true in the world) and a system time (when we recorded it). "As of date X" is a stock query. Two SQL functions, kndb.as_of_valid() and kndb.as_of_believed(), answer the natural historical questions in one line.

Analogy · a newspaper archive with corrections You can read the article as printed on March 5 (what we thought that day) or the correction issued March 12 (what turned out to be true). Both are queryable, neither is lost.
Traditional DB

Corrections mutate the article in place. Ask "what did the March 5 paper say?" and you get what we think NOW, not what was on the newsstand then. Audits require reading the write-ahead log by hand.

KNDB

Both the March 5 belief and the March 12 correction live in the table with their respective time ranges. Either question is a stock query. Audits are ordinary SQL.

Regulatory audit

Regulator asks: was Jane properly enrolled in the trial on Feb 15 based on what you knew then? In plain Postgres the DB shows only current state; a Mar 20 correction masks the Feb 15 belief. In KNDB, as_of_believed('2026-02-15', '2026-02-15') returns exactly what the trial team saw at enrollment. Decision defended in one query.

Insurance policy effective dates

Policy is effective April 1 through June 30 but was recorded on February 15. When the claim comes in for a May incident: was the coverage in force? Two different times, two different questions, both must be answerable.

5

Progressive-depth queries

One SQL function, kndb.expand(entity, depth), controls how much to trust. Depth 0 returns only observations. Depth 1 adds inferences. Depth 2 adds derived aggregates. Recall goes up, average confidence goes down, monotonically.

Analogy · ER triage Same waiting room, three lanes. Immediate (only confirmed observations). Urgent (also model-flagged). Non-urgent (also derived signals). One knob, the same data, the right people first.
Traditional DB

Every filter is a different query. Strict-mode team writes WHERE hba1c >= 6.5. Broad-mode team copies and adds OR is_diabetic_pred = 1. Each team's numbers diverge over time.

KNDB

One knob. kndb.expand(depth=0) = 492 patients from our real Synthea run. depth=1 adds model-predicted diabetics. depth=2 adds patients with derived 90-day-avg HbA1c ≥ 6.5. Same query shape, one integer changes.

Support ticket triage

Emergency queue: only observations from the customer (they explicitly said the outage is affecting them). Broader queue: also model-inferred impact. Broadest queue: also derived signals like "this account's error rate is up 3x." Reviewers pick their confidence appetite per shift.

Content moderation

Depth 0: user reports. Depth 1: model-flagged posts. Depth 2: derived signals like account age percentiles. Moderators tune the tradeoff without reimplementing filters every quarter.

05 · architecture

How it’s built

KNDB is a Postgres extension pattern, not a new server. Any team that already runs Postgres can adopt it without swapping infrastructure. The engine sits between the client and the fact table as a set of triggers and typed columns.

Client layer
psql, ORM (SQLAlchemy, Prisma, Django ORM), agent memory writers (Zep, Graphiti, MCP tool servers), MLOps pipelines (dbt, Airflow, Prefect). Every write goes through the same triggers, so no client can bypass the rules.
Write-time enforcement (PL/pgSQL triggers)
BEFORE INSERT / UPDATE triggers enforce five rules:
  R1 — derived rows must name at least one source.
  R2 — every source must resolve to an existing fact.
  R3 — observations cannot have sources.
  R4 — inferences cannot claim confidence = 1.0.
  R5 — slot-kind registry must agree with the row's kind.
Conflict detection is another BEFORE trigger: overlapping valid-time with a different value either invalidates the loser (audit-preserved) or rejects the write.
The fact table — kndb.fact
Columns: entity_id, attribute, value, epistemic_kind (ENUM), confidence (0-1 domain), sources uuid[], valid_time tstzrange, sys_time tstzrange, and a hidden provsql UUID token. A GiST exclusion constraint enforces no-overlap on (entity_id, attribute, valid_time). Audit sits in a sibling table kndb_audit.evicted_fact.
Confidence propagation — ProvSQL 1.10.0 extension
An AFTER trigger keeps set_prob(token, confidence) in lockstep with the row's confidence. Query-side helpers call sr_viterbi(provenance(), weights_tbl) to compute joined confidence across arbitrary joins. Standard SQL joins work as usual; the semiring evaluation is opt-in per query.
Query surface
kndb.as_of_valid(entity, attribute, ts) for "what did we believe held at time X."
kndb.as_of_believed(entity, attribute, valid_ts, sys_ts) for "what did we know on system-time Y."
kndb.expand(entity, depth) for progressive-depth queries.
Everything else is ordinary SQL.

06 · status

What runs today Green

All numbers below come from actual runs, seed 42, on native ARM64 Postgres 17.10 + ProvSQL 1.10.0. Nothing extrapolated.

  • Five primitives implemented in ~600 lines of SQL / PL-pgSQL.
  • 15 sub-tests across 7 files, all pass. Every write-time rule proved by failing-test-first.
  • Synthea v4.0.0 generates 11,637 patients (SHA256 verified). Loaded into typed kndb.fact: 544,349 observations, 4,999 inferences, 16,239 derived.
  • Real-data attack: model-imputed HbA1c into an obs-typed slot is rejected at write time with rule R5.
  • CI green on hosted GitHub runner, 5 consecutive runs, ~1m 57s each.

Benchmark against three baselines

System Adversarial catch Confidence drift Guard LOC p50 latency Throughput
KNDB 70 / 70 ~0 (fp noise) 150 68 μs (empty) · 70 μs (565k Synthea) 13,150 rps · 5,597 rps
Plain Postgres 0 / 70 0.210 0 — —

Two findings from the benchmark worth calling out:

  1. A hand-rolled trigger suite can catch every adversarial write in 124 lines of PL/pgSQL. KNDB's value is that those primitives ship as one coherent tested package, so every project doesn't reimplement them from scratch (and get subtly different answers each time).
  2. KNDB write throughput drops with table size (13,150 to 5,597 rps at 565k rows). The steelman is size-invariant. The gap is ProvSQL's set_prob map growing with the table — the measurable cost of engine-computed confidence propagation.

08 · try it

Fifteen minutes and you have it running

git clone git@github.com:emailvenkatm/kndb.git
cd kndb
make up            # starts isolated Postgres + ProvSQL on port 5433
make engine        # applies engine/*.sql
make test          # 15/15 sub-tests pass
make demo          # the 60-second trust story

For the real clinical scenario on 11,637 Synthea patients:

bash data/generate.sh       # downloads Synthea v4.0.0 (SHA256 verified)
python3 data/synthesize_labels.py
bash data/load_postgres.sh
bash demo/demo_clinical.sh  # attack + eligibility screening on real data

For the benchmark:

bash bench/run_native.sh       # native (no emulation) if brew Postgres is installed
bash bench/run_synthea.sh      # same benchmark on 565k Synthea-preloaded rows

A running status of what is measured vs what is still in progress is in STATUS.md at the repo root.
